# Stalwart Mail & Calendar Web UI end-to-end test plan

This runbook installs Stalwart from the source tree, completes its bootstrap setup, installs the standalone Mail & Calendar Web UI with its own installer, and tests mail, calendar, and invitation behavior against the real server.

The main path targets an isolated Ubuntu 24.04 test host. It keeps the test services on loopback through an SSH tunnel and uses the reserved `example.test` domain, so it is not a production mail-server deployment guide. Production requires public DNS, trusted TLS, a reverse proxy or public listener design, backups, and a separate security review.

## 1. Test objective

Prove all of the following on a clean host:

1. A pinned Stalwart revision builds into the `stalwart` binary with the RocksDB backend.
2. Stalwart can bootstrap, persist its configuration, and expose Mail, Submission, and Calendars through JMAP.
3. The standalone Web UI installs without using or changing Stalwart's installer.
4. A user can connect by entering the Stalwart server address and an app password.
5. OAuth Authorization Code with PKCE works when anonymous dynamic client registration is enabled for the test.
6. Mail reading, search, composition, drafts, attachments, message actions, and safe HTML rendering work.
7. Calendar day, week, month, and agenda views can create, edit, and delete events, and an organizer can invite guests by email from the event form.
8. A received invitation is easy to add or answer from the message.
9. An unanswered invitation is shown at roughly half emphasis, an accepted invitation is solid, a tentative invitation is reduced in emphasis, and a declined invitation remains visible but faint, hatched, and struck through.
10. RSVP changes are stored by Stalwart and propagated back to the organizer.

## 2. Scope and acceptance rules

### In scope

- Stalwart `0.16.16` as declared by `crates/main/Cargo.toml`, or the exact revision recorded at test start
- RocksDB, the source tree's default local data backend
- The Web UI in this repository's `webui/` directory
- Chromium and Firefox on desktop
- One narrow viewport at 390 × 844 CSS pixels
- Basic authentication with a Stalwart app password
- OAuth with PKCE in a test-only configuration
- Local-to-local JMAP scheduling and an email-only external iMIP invitation
- Organizer-created invitations sent from the Web UI event form

### Out of scope for this local run

- Public DNS reputation and internet delivery
- ACME certificate issuance
- Load, soak, failover, backup/restore, and multi-node tests
- External LDAP, SQL, or OIDC directories
- Mobile native applications
- Safari, unless a macOS test host is available

### Entry criteria

- A fresh VM or disposable host with at least 4 CPU cores, 8 GB RAM, and 20 GB free disk
- Ubuntu 24.04 with `sudo` access
- Outbound HTTPS to GitHub, `objects.githubusercontent.com`, crates.io, Rust distribution servers, NodeSource, and nodejs.org
- Ports 25, 443, 465, 993, 995, 4190, 8080, and 8081 unused on the test host
- A browser machine that can open an SSH tunnel to the test host
- No real credentials or production data used in this run

### Exit criteria

- Every P0 and P1 case in the execution matrix passes
- No unresolved severity 1 or severity 2 defects
- No uncaught browser-console error during the core flows
- No credential, access token, message body, or calendar body appears in the diagnostics screen or service logs generated by normal use
- The Stalwart JMAP response advertises Core, Mail, Submission, Calendars, and Calendar parsing capabilities
- Test evidence and the exact source revision are attached to the test report

## 5. Phase A: prepare and build Stalwart from source

### A1. Install compiler prerequisites

Install the packages used by the repository's Linux container build plus common native-build requirements for RocksDB and AWS-LC:

```bash

  build-essential ca-certificates clang cmake curl git libclang-dev \
  perl pkg-config xz-utils jq
```

Install the current stable Rust toolchain with the minimal rustup profile:

```bash
curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs \

sh /var/tmp/rustup-init.sh -y --profile minimal --default-toolchain stable

rustc --version
cargo --version
```

Expected: both commands print versions, and Rust supports edition 2024. The official [compiling Stalwart guide](https://stalw.art/docs/development/compile/) also requires the latest Rust toolchain and recommends testing a tagged release rather than an unpinned moving branch.

### A2. Pin and record the source revision

Use the checkout containing this Web UI. Replace the example path if needed:

```bash
export STALWART_SRC=/home/tester/stalwart
cd "$STALWART_SRC"
git fetch --tags --prune
git rev-parse HEAD
git describe --tags --always
git status --short
```

For a release qualification run, check out the release tag being qualified. For a development run, check out the exact commit supplied by engineering. Never report a result against an unspecified `main` branch state.

Record the baseline:

```bash

  uname -a
  rustc --version
  cargo --version
  git rev-parse HEAD
  git describe --tags --always

```

Expected: `Cargo.toml`, `Cargo.lock`, `crates/main/`, and `webui/` exist. Any local modification must be explained in the result sheet.

### A3. Compile the server

Build an open-source binary with only the RocksDB storage feature required by this test:

```bash
cd "$STALWART_SRC"
cargo build --locked --release -p stalwart \
  --no-default-features --features rocks
target/release/stalwart --version
```

Expected:

- The build exits with status 0.
- `target/release/stalwart` exists and is executable.
- `stalwart --version` prints `0.16.16` for this source snapshot.

Record the checksum:

```bash
sha256sum target/release/stalwart | tee "$TEST_RUN_DIR/stalwart.sha256"
```

If the build fails in `librocksdb-sys`, confirm `clang`, `libclang-dev`, `cmake`, and a C++ compiler are installed, then rerun the same locked build. Do not remove `Cargo.lock` to work around a dependency error.

## 6. Phase B: install and bootstrap the source-built Stalwart binary

### B1. Confirm the host is clean

```bash
sudo ss -ltnp | grep -E ':(25|443|465|993|995|4190|8080|8081)\b' || true
```

Expected: no listener occupies the listed ports. Use a fresh VM if another mail server is installed; do not stop an unknown service just to continue this test.

### B2. Create the service account and directories

```bash
getent group stalwart >/dev/null || sudo groupadd --system stalwart
id stalwart >/dev/null 2>&1 || sudo useradd \
  --system --gid stalwart --home-dir /var/lib/stalwart-source-test \
  --shell /usr/sbin/nologin stalwart

sudo install -d -m 0755 -o root -g root /opt/stalwart-source-test/bin
sudo install -d -m 0750 -o stalwart -g stalwart \
  /etc/stalwart-source-test \
  /var/lib/stalwart-source-test/data \
  /var/log/stalwart-source-test
sudo install -m 0755 target/release/stalwart \
  /opt/stalwart-source-test/bin/stalwart
```

The configuration file must not exist on first start. Its absence causes Stalwart to enter bootstrap mode and expose the setup wizard on port 8080.

### B3. Create the bootstrap environment file

Create `/etc/stalwart-source-test/stalwart.env` with owner `root:stalwart`, mode `0640`, and this content:

```text
STALWART_HOSTNAME=mail.example.test
STALWART_PUBLIC_URL=http://127.0.0.1:8080
STALWART_RECOVERY_ADMIN=admin:REPLACE-WITH-A-LONG-RANDOM-LAB-PASSWORD
```

Commands:

```bash
sudo install -m 0640 -o root -g stalwart /dev/null \
  /etc/stalwart-source-test/stalwart.env
sudoedit /etc/stalwart-source-test/stalwart.env
```

`STALWART_PUBLIC_URL` makes every JMAP and OAuth URL point to the browser's loopback tunnel. Plain HTTP is acceptable only for this loopback test. `STALWART_RECOVERY_ADMIN` avoids losing a one-time random bootstrap password in logs; remove it after the wizard completes.

### B4. Create and start the source-build service

Create `/etc/systemd/system/stalwart-source-test.service`:

```ini
[Unit]
Description=Stalwart source-build end-to-end test
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=stalwart
Group=stalwart
WorkingDirectory=/var/lib/stalwart-source-test
EnvironmentFile=/etc/stalwart-source-test/stalwart.env
ExecStart=/opt/stalwart-source-test/bin/stalwart --config=/etc/stalwart-source-test/config.json
Restart=on-failure
RestartSec=5
LimitNOFILE=65536
AmbientCapabilities=CAP_NET_BIND_SERVICE
CapabilityBoundingSet=CAP_NET_BIND_SERVICE

[Install]
WantedBy=multi-user.target
```

Install and start it:

```bash
sudoedit /etc/systemd/system/stalwart-source-test.service
sudo systemctl daemon-reload
sudo systemctl enable --now stalwart-source-test.service
sudo systemctl status --no-pager stalwart-source-test.service
curl -fsS http://127.0.0.1:8080/healthz/live
```

Expected: the service is active, health returns an HTTP 200 response, and the logs contain `bootstrap mode`.

```bash
sudo journalctl -u stalwart-source-test -n 200 --no-pager
```

If `/admin/` returns 404, inspect the logs for a failure to fetch the built-in administration bundle. Bootstrap setup depends on outbound HTTPS to GitHub and its release-object host.

### B5. Open the bootstrap wizard through an SSH tunnel

On the browser machine, keep this command running:

  -L 8080:127.0.0.1:8080 \
  -L 8081:127.0.0.1:8081 \

Open `http://127.0.0.1:8080/admin/` and sign in with the bootstrap credential from the environment file.

Complete the five-screen wizard with these test values:

   - Default domain: `example.test`
   - Request a TLS certificate: off
   - DKIM generation: either value is acceptable for this local run

   - Use the Internal Directory
4. Logging

Record the permanent administrator username and generated password from the completion screen. The wizard writes `/etc/stalwart-source-test/config.json` and provisions a permanent administrator. This behavior is described in the official [Linux bootstrap instructions](https://stalw.art/docs/install/platform/linux/) and is implemented by the source in `crates/jmap/src/registry/mapping/bootstrap.rs`.

Restart and verify normal mode:

```bash

sudo systemctl status --no-pager stalwart-source-test.service
sudo test -s /etc/stalwart-source-test/config.json

```

Expected: health returns 200, the config file is nonempty, and the new logs no longer say that no configuration file was found.

### B7. Configure browser access from the standalone UI

The standalone UI is a different origin, so the browser requires Cross-Origin Resource Sharing (CORS) response headers. CORS is the browser rule that blocks one site from calling another unless the target server opts in.

In the Stalwart admin console, open **Settings › Network › HTTP › General** and set these response headers:

```json
{
  "Access-Control-Allow-Origin": "http://127.0.0.1:8081",
  "Access-Control-Allow-Headers": "Authorization, Content-Type, Accept, X-Requested-With",
  "Access-Control-Allow-Methods": "POST, GET, PATCH, PUT, DELETE, HEAD, OPTIONS"
}
```

Use the exact origin above throughout the test. Do not switch between `localhost` and `127.0.0.1`; they are different browser origins. The field is `responseHeaders` on Stalwart's `Http` singleton. The alternative `usePermissiveCors=true` sends a wildcard origin and is broader than this test needs. See the official [HTTP security](https://stalw.art/docs/http/security/) and [HTTP object](https://stalw.art/docs/ref/object/http/) references.

For AUTH-02 only, open **Settings › Authentication › OIDC Provider** and set `anonymousClientRegistration` to `true`. The current standalone UI registers a public OAuth client dynamically before starting PKCE. This setting is off by default because anonymous registration widens the attack surface. Disable it after the OAuth case unless the deployment has explicitly accepted that policy. See [Dynamic Registration](https://stalw.art/docs/auth/oauth/client-registration/).

Save, restart Stalwart, and verify preflight from the host:

```bash
sudo systemctl restart stalwart-source-test.service
curl -i -X OPTIONS http://127.0.0.1:8080/jmap/ \
  -H 'Origin: http://127.0.0.1:8081' \
  -H 'Access-Control-Request-Method: POST' \
  -H 'Access-Control-Request-Headers: authorization,content-type'
```

Expected: status 200 or 204 and all three configured `Access-Control-Allow-*` headers. A missing allow-origin or allow-headers value is a blocker for browser tests.

## 8. Phase D: seed deterministic invitation data

Run this phase only after both accounts can open the Calendar screen once. That first access creates each account's default calendar if it does not already exist.

### D1. Create a local organizer-to-attendee invitation through JMAP

Enter the organizer app password in the same private shell:

```bash
export ORGANIZER_EMAIL=organizer@example.test
read -rsp 'Organizer app password: ' ORGANIZER_SECRET
printf '\n'
```

Discover the organizer's JMAP account and default calendar:

```bash
ORGANIZER_SESSION=$(curl -fsS \
  --user "$ORGANIZER_EMAIL:$ORGANIZER_SECRET" \
  -L http://127.0.0.1:8080/.well-known/jmap)

JMAP_API_URL=$(printf '%s' "$ORGANIZER_SESSION" | jq -r '.apiUrl')
ORGANIZER_ACCOUNT_ID=$(printf '%s' "$ORGANIZER_SESSION" | jq -r \
  '.primaryAccounts["urn:ietf:params:jmap:calendars"]')

CALENDAR_REQUEST=$(jq -nc --arg account "$ORGANIZER_ACCOUNT_ID" '
  {
    using: [
      "urn:ietf:params:jmap:core",
      "urn:ietf:params:jmap:calendars"
    ],
    methodCalls: [[
      "Calendar/get",
      {accountId: $account, properties: ["id", "name"]},
      "calendar"
    ]]
  }')

CALENDAR_RESPONSE=$(curl -fsS \
  --user "$ORGANIZER_EMAIL:$ORGANIZER_SECRET" \
  -H 'Content-Type: application/json' \
  --data "$CALENDAR_REQUEST" \
  "$JMAP_API_URL")

ORGANIZER_CALENDAR_ID=$(printf '%s' "$CALENDAR_RESPONSE" | jq -er \
  '.methodResponses[] | select(.[2] == "calendar") | .[1].list[0].id')
printf 'Organizer account=%s calendar=%s\n' \
  "$ORGANIZER_ACCOUNT_ID" "$ORGANIZER_CALENDAR_ID"
```

If the calendar list is empty, sign in to the standalone Web UI as the organizer, open Calendar once, refresh, and rerun the query.

Create a one-hour invitation for tomorrow:

```bash
INVITE_START=$(date -u -d 'tomorrow 10:00' '+%Y-%m-%dT%H:%M:%S')
INVITE_UID="webui-local-$(date -u +%s)@example.test"

EVENT_REQUEST=$(jq -nc \
  --arg account "$ORGANIZER_ACCOUNT_ID" \
  --arg calendar "$ORGANIZER_CALENDAR_ID" \
  --arg uid "$INVITE_UID" \
  --arg start "$INVITE_START" '
  {
    using: [
      "urn:ietf:params:jmap:core",
      "urn:ietf:params:jmap:calendars"
    ],
    methodCalls: [[
      "CalendarEvent/set",
      {
        accountId: $account,
        sendSchedulingMessages: true,
        create: {
          invite: {
            "@type": "Event",
            uid: $uid,
            title: "Web UI pending invitation",
            description: "Invitation state acceptance test",
            start: $start,
            duration: "PT1H",
            timeZone: "Etc/UTC",
            freeBusyStatus: "busy",
            calendarIds: {($calendar): true},
            organizerCalendarAddress: "mailto:organizer@example.test",
            participants: {
              "11111111-1111-4111-8111-111111111111": {
                "@type": "Participant",
                name: "Organizer",
                calendarAddress: "mailto:organizer@example.test",
                roles: {chair: true},
                participationStatus: "accepted"
              },
              "22222222-2222-4222-8222-222222222222": {
                "@type": "Participant",
                name: "Attendee",
                calendarAddress: "mailto:attendee@example.test",
                kind: "individual",
                expectReply: true,
                participationStatus: "needs-action"
              }
            }
          }
        }
      },
      "create-invite"
    ]]
  }')

EVENT_RESPONSE=$(curl -fsS \
  --user "$ORGANIZER_EMAIL:$ORGANIZER_SECRET" \
  -H 'Content-Type: application/json' \
  --data "$EVENT_REQUEST" \
  "$JMAP_API_URL")

printf '%s' "$EVENT_RESPONSE" | jq .
ORGANIZER_EVENT_ID=$(printf '%s' "$EVENT_RESPONSE" | jq -er \
  '.methodResponses[] | select(.[2] == "create-invite") | .[1].created.invite.id')
```

Expected: the server returns an event ID. Within a few seconds the attendee receives an email with `event.ics`, and the event is automatically present in the attendee calendar with `needs-action`. This path follows the same `CalendarEvent/set` plus `sendSchedulingMessages` behavior covered by `tests/src/jmap/calendar/notification.rs`.

### D2. Send an email-only invitation that is not auto-added

In **Settings › Calendar & Contacts › Scheduling**, confirm scheduling is enabled and `autoAddInvitations` is `false`. Ensure `outside@example.net` is not in the attendee's address book. Stalwart's default policy does not auto-add an external invitation from an unauthenticated sender that is absent from the recipient's contacts.

Create a MIME message with a calendar attachment:

```bash
EXTERNAL_START=$(date -u -d '2 days 14:00' '+%Y%m%dT%H%M%SZ')
EXTERNAL_END=$(date -u -d '2 days 15:00' '+%Y%m%dT%H%M%SZ')
EXTERNAL_UID="webui-external-$(date -u +%s)@example.net"
BOUNDARY="webui-e2e-$(date -u +%s)"

cat > "$TEST_RUN_DIR/external-invite.eml" <<EOF
From: External Organizer <outside@example.net>
To: Attendee <attendee@example.test>
Date: $(date -R)
Message-ID: <$EXTERNAL_UID>
Subject: Email-only Web UI invitation
MIME-Version: 1.0
Content-Type: multipart/mixed; boundary="$BOUNDARY"

--$BOUNDARY
Content-Type: text/plain; charset=UTF-8

Please review this invitation in the standalone Web UI.

--$BOUNDARY
Content-Type: text/calendar; method=REQUEST; charset=UTF-8
Content-Disposition: attachment; filename="event.ics"
Content-Transfer-Encoding: 8bit

BEGIN:VCALENDAR
VERSION:2.0
PRODID:-//Stalwart Web UI E2E//EN
METHOD:REQUEST
BEGIN:VEVENT
UID:$EXTERNAL_UID
DTSTAMP:$(date -u '+%Y%m%dT%H%M%SZ')
DTSTART:$EXTERNAL_START
DTEND:$EXTERNAL_END
SUMMARY:Email-only Web UI invitation
DESCRIPTION:This event should not exist until the attendee adds it.
LOCATION:Test room
ORGANIZER;CN=External Organizer:mailto:outside@example.net
ATTENDEE;CN=Attendee;PARTSTAT=NEEDS-ACTION;RSVP=TRUE:mailto:attendee@example.test
END:VEVENT
END:VCALENDAR

--$BOUNDARY--
EOF
```

Submit it as unauthenticated external SMTP to the local recipient:

```bash
curl --fail --show-error --silent --crlf \
  --url smtp://127.0.0.1:25 \
  --mail-from outside@example.net \
  --mail-rcpt attendee@example.test \
  --upload-file "$TEST_RUN_DIR/external-invite.eml"
```

Expected: the message is delivered, but no event with `EXTERNAL_UID` appears in the attendee calendar before the user acts. Check Junk or All Mail if filtering moves the message. This tests the important email-only import path separately from Stalwart's trusted local scheduling path. The policy is documented under [Scheduling and automatic event addition](https://stalw.art/docs/collaboration/scheduling/).

After each change, query the organizer's event to prove server-side propagation:

```bash
STATUS_REQUEST=$(jq -nc \
  --arg account "$ORGANIZER_ACCOUNT_ID" \
  --arg id "$ORGANIZER_EVENT_ID" '
  {
    using: [
      "urn:ietf:params:jmap:core",
      "urn:ietf:params:jmap:calendars"
    ],
    methodCalls: [[
      "CalendarEvent/get",
      {accountId: $account, ids: [$id], properties: ["id", "uid", "participants"]},
      "status"
    ]]
  }')

curl -fsS \
  --user "$ORGANIZER_EMAIL:$ORGANIZER_SECRET" \
  -H 'Content-Type: application/json' \
  --data "$STATUS_REQUEST" \
  "$JMAP_API_URL" \
  | jq '.methodResponses[] | select(.[2] == "status") | .[1].list[0]'
```

Pass when the attendee participant moves through `accepted`, `tentative`, and `declined` on the organizer copy, and the Web UI never creates a second event for the same UID.

## 11. Troubleshooting decision table

| Symptom | Likely cause | Check | Corrective action |
|---|---|---|---|
| Rust build cannot find Clang | RocksDB bindgen dependency missing | `clang --version`; locate `libclang.so` | Install `clang` and `libclang-dev`, then rerun the locked build |
| Stalwart exits after wizard | Privileged default listeners cannot bind, or port conflict | `journalctl`; `ss -ltnp` | Confirm the unit has `CAP_NET_BIND_SERVICE` and use a clean host |
| `/admin/` is 404 during bootstrap | Built-in admin bundle was not downloaded | Stalwart resource errors in journal | Permit outbound HTTPS to GitHub release storage and restart |
| JMAP publishes `https://mail.example.test` | Public URL override missing | Inspect `.apiUrl` in session JSON | Restore `STALWART_PUBLIC_URL=http://127.0.0.1:8080` and restart |
| Browser says it cannot reach JMAP | CORS, TLS, wrong URL, or mixed `localhost`/`127.0.0.1` | Preflight curl and DevTools Network | Use the exact origin and fix all three allow headers |
| OAuth registration fails | Anonymous dynamic registration disabled | `/auth/register` response | Enable `anonymousClientRegistration` for AUTH-02 or use app-password login |
| Mail works but Calendar is absent | Calendar capability or permissions missing | Authenticated JMAP session | Restore the user's default role/calendar permissions and refresh |
| Invitation email has no card | No `text/calendar` attachment or parse capability | Message attachment type; session capabilities | Fix the fixture/server capability and rerun without manually importing it |
| Local invite email arrives but event is absent | Scheduling task delayed or failed | Scheduled tasks and Stalwart logs | Confirm scheduling is enabled and inspect iTIP task errors |
| External invitation auto-adds unexpectedly | Sender trusted, in contacts, or global auto-add enabled | Scheduling config and attendee contacts | Set `autoAddInvitations=false`, use a new external sender, and remove it from contacts |
| RSVP changes UI but not organizer | Scheduling task failed | Organizer JMAP query and task logs | Treat as INV-02 failure; capture task error and both event IDs |
| Installer reports health failure but unit soon becomes active | Start/health timing race | `systemctl status`; retry health after one second | Record an installer defect even if manual health later passes |

## 13. Cleanup and retention

Stop the SSH tunnel and unset shell secrets:

```bash
unset ATTENDEE_SECRET ORGANIZER_SECRET
```

On a disposable host, stop the test services:

```bash
sudo systemctl disable --now stalwart-webui.service
sudo systemctl disable --now stalwart-source-test.service
```

Do not delete `/var/lib/stalwart-source-test`, `/etc/stalwart-source-test`, `/opt/stalwart-source-test`, `/opt/stalwart-webui`, or the evidence directory until the run is signed off. Those paths contain the database, configuration, exact installed binaries, and failure evidence needed to reproduce a defect. Destroy the disposable VM only after the report and required artifacts are retained.
